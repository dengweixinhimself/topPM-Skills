# Product Insight Miner

把分散的用户声音整理成可验证的产品机会。核心产物不是链接列表，而是：

1. 可回溯的用户素材池；
2. 按痛点聚类的需求证据；
3. 竞品盲区和机会假设；
4. 下一轮访谈、原型或 BRD 应验证的关键问题。

## 先判断是否适用

适用：

- 用户想发现痛点、需求、替代方案或产品机会；
- 用户提供 Reddit、X、公众号、小红书、应用商店评论、客服记录、访谈或截图；
- 用户要比较某个品类的真实反馈，或要生成调研报告。

不适用：

- 只问一个产品的简单评价；
- 只要市场规模、商业可行性或正式 BRD：交给 `brd`；
- 已经有明确需求，只要正式 MRD：交给 `mrd`；
- 要拆解单个产品的实现方式：交给 `ai-product-teardown`。

## 研究模式

### A. 公开资料搜索

用户没有素材时，使用当前环境可用的搜索、浏览器或连接器能力。不要假设某个工具一定存在，先使用可用能力；如果无法访问某个平台，记录限制并切换来源或请求用户手动补充。

优先顺序：

1. 用户原始材料和一手用户帖子；
2. 帖子评论、应用商店评论、社区讨论和产品反馈页；
3. 官方产品页、帮助文档、定价页和隐私政策，用于确认产品能力；
4. 搜索结果摘要、转载和二手文章，只作为线索，不能当作用户原话。

### B. 手动素材投喂

用户粘贴链接、文字或截图时，立即归档，不要求先做完整搜索。链接无法打开时，保留用户提供的内容，并把来源状态标为“用户提供，待复核”。

### C. 混合模式

先搜索建立方向，再让用户补充缺失平台、语言、应用场景或目标用户。每轮都更新素材池，不重复采集已经覆盖的角度。

## 工作流程

### 1. 明确研究合同

只询问会改变研究结果的问题。若用户已经说明，不重复问。至少确认：

- 研究主题或品类；
- 目标用户；
- 地区、语言和平台范围；
- 已知竞品或替代方案；
- 交付物：对话摘要、Markdown、HTML 或继续进入 BRD/MRD。

信息不足时，默认“全体用户广泛扫描”，并在报告中标注默认范围。不要为了形式凑问题。

### 2. 设计搜索计划

围绕四个角度各准备查询：

- 痛点：难用、失望、出错、浪费时间、隐私担忧；
- 方案请求：有没有替代、怎么解决、推荐什么；
- 竞品迁移：替代某产品、取消订阅、离开、为什么没人做；
- 价值与付费：愿意付费、刚需、值得订阅、希望有人做。

先做一轮广搜，再用出现频率高的竞品名、场景词和痛点词做一轮聚焦。详细查询模板见 [references/search-strategy.md](references/search-strategy.md)。

停止条件：每个主要方向至少有 2 条独立证据，且出现至少一个反例、限制或未验证假设；如果只有搜索摘要或同一来源重复转载，不得宣称“已验证”。

### 3. 归档素材

为每条素材分配稳定 ID，例如 `R01`、`X03`、`H02`、`O01`：

```text
素材 ID：R01
平台：Reddit
URL：完整链接
发布时间：可确认时填写，否则“未知”
来源状态：E2 原帖 / E1 官方页面 / E0 搜索线索 / 用户提供待复核
用户类型：能确认时填写，不要猜测
场景：用户正在做什么
摘要：客观转述，不夹带结论
原文引用：只填写页面中可核对的原句；搜索摘要不能放这里
信号类型：痛点 / 方案请求 / 竞品吐槽 / 付费意愿 / 改进建议 / 反例
情绪强度：1-5
证据备注：互动量、评论共识、是否跨平台出现
```

每轮归档后向用户报告：素材总数、来源分布、覆盖的痛点方向、访问失败的平台和下一步选择。不要编造互动量、发布时间、用户身份或原句。

### 4. 分析与评分

先把素材分为“事实”“推断”“待验证假设”，再聚类。每个痛点簇至少包含：

- 簇名称和一句话定义；
- 场景、触发、后果和当前替代方案；
- 素材 ID 列表和跨来源情况；
- 代表性原话（只有 E2/E3 才能引用）；
- 反例或不支持该结论的素材；
- 频率、强度、证据置信度和评分依据。

评分规则：

- 频率 1-5：只按去重后的独立来源计数；同一帖子的评论不能自动算多个独立用户；
- 强度 1-5：根据明确损失、替代行为、迁移意愿和付费表达评分；
- 优先级 = 频率 × 强度；
- 置信度：高（多来源 E2/E3 交叉验证）、中（单平台多条或官方能力与用户反馈对上）、低（E0/E1 线索或样本很小）。

没有足够素材支撑时，显示“样本不足”，不要用 1-5 分制造虚假的精确感。

### 5. 提炼产品机会

最多输出 3 个机会，每个机会必须写清：

- 目标用户和高频场景；
- 被解决的具体问题；
- 为什么现有方案没有充分解决；
- 最小可验证方案；
- 需要验证的关键假设；
- 主要风险（技术、分发、隐私、竞争、付费）；
- 支撑它的素材 ID。

机会是待验证假设，不写成已经成立的市场事实。用户要判断“值不值得做”时，建议把结果交给 `brd`；用户要继续梳理需求时，交给 `mrd`。

### 6. 交付报告

用户说“生成报告”“做成 HTML”或明确要可视化时，读取 [references/report-template.md](references/report-template.md)。报告至少包含：

- 研究范围、日期、素材统计和限制；
- 执行摘要；
- 证据质量说明；
- 痛点聚类和优先级矩阵；
- 竞品/替代方案盲区；
- TOP 3 机会与验证计划；
- 可折叠的原始素材和来源链接。

HTML 必须是单文件、内联 CSS/JS、无外部依赖、响应式、可直接打开。若用户未指定目录，保存到当前工作区的 `outputs/product-insight-report-<slug>-<YYYY-MM-DD>.html`；不要写死 `/mnt/user-data/outputs`。生成后检查文件存在、HTML 闭合、链接可读，并向用户提供文件链接。

## 证据纪律

- 不把搜索结果摘要、SEO 文案或转载文章写成用户原话；
- 不把官方产品能力写成用户满意度；
- 不把少量帖子推断成总体比例、市场规模或付费率；
- 不隐藏访问失败、样本偏差、语言偏差和时间范围；
- 事实挂素材 ID，推断写出推理链，假设列出验证方式；
- 原文引用保持原语言，翻译放在括号内并标记为译文；
- 涉及隐私、医疗、金融或安全时，优先引用原始政策和实际用户反馈，避免提供未经证实的保证。

## 对话节奏

搜索或整理过程中给短进度，不用每个链接都打断用户。每轮完成后回答三件事：

1. 新增了什么证据；
2. 当前最强的 1-3 个信号是什么；
3. 还缺什么证据，下一步是继续搜索、补素材还是生成报告。
